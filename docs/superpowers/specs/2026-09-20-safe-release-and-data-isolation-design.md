# 波波工单安全发布与数据隔离设计

## 目标

将 `D:\波波本地联调` 整理为波波工单唯一的开发和发布主线，将 `D:\codex内容\copy黑湖小工单` 冻结为旧线上代码基线。今后的正式发布只能升级代码，不能覆盖线上数据库、附件、密钥或日志，并且必须能够在健康检查失败时恢复到上一代码版本。

## 当前状态

- 两个目录的 Git 基准提交均为 `624c38a`，但分别包含不同的未提交修改，不能再用提交号判断实际版本。
- 本地联调版已经包含平台订单、来源渠道、工序回调和本地持久化集成配置。
- 旧线上基线版不包含完整的平台订单回调数据结构。
- 两个目录的 `data/db.json` 内容和结构不同，不能互相复制。
- 当前本地运行默认使用 JSON 数据库；代码同时保留 MySQL 驱动入口。

## 仓库角色

### 唯一主线

`D:\波波本地联调` 是唯一允许继续开发、测试、提交和生成发布包的目录。

所有待发布代码必须满足：

1. 已进入 Git 提交。
2. 工作区没有未提交修改。
3. 完整自动化测试通过。
4. 发布包通过敏感文件和运行时数据检查。

### 冻结基线

`D:\codex内容\copy黑湖小工单` 只用于保存旧线上代码快照和回滚参考，不继续开发。整理时生成代码快照、文件清单和 SHA-256 校验文件，但不复制该目录的业务数据进入主线。

## 版本策略

- 使用语义化版本号：`bobo-v<major>.<minor>.<patch>-<name>`。
- 首个包含平台订单集成的候选版本命名为 `bobo-v0.3.0-platform-integration`。
- 每个发布包必须记录：版本号、Git 完整提交号、构建时间、构建机器和文件 SHA-256。
- Git 标签只能指向测试通过且工作区干净的提交。
- 发布包只能从指定提交生成，不能直接压缩当前目录。

## 运行时数据边界

以下内容属于运行时数据，永远不能进入发布包：

- `data/`
- `db/`
- `public/uploads/`
- `config.local.json`
- `.env` 和任何环境配置文件
- `*.log`、`*.pid`、`*.tmp`
- 本地备份、部署产物和工具缓存

生产服务器采用固定数据目录：

```text
/srv/bobo/
├── releases/
├── current -> releases/<version>/
├── shared/
│   ├── data/
│   └── uploads/
├── backups/
└── logs/
```

每个发布目录中的 `data` 和 `public/uploads` 必须链接到 `shared/data` 与 `shared/uploads`。生产密钥通过 systemd 的 `EnvironmentFile` 提供，不写入发布目录。

## 发布包构建

Windows 构建脚本 `scripts/build-release.ps1` 接收明确的版本号并执行以下步骤：

1. 验证当前目录是唯一主线仓库。
2. 验证 Git 工作区干净。
3. 运行完整测试集。
4. 从 Git 提交导出受版本控制的文件。
5. 删除并检查所有运行时数据路径和敏感文件模式。
6. 写入 `release-manifest.json`。
7. 生成 ZIP 和同名 `.sha256` 文件。
8. 再次检查 ZIP 内容；发现禁止路径时删除产物并失败。

发布包采用拒绝列表与最终内容检查双重保护。构建脚本不读取、复制或打印密钥内容。

## 生产部署

Linux 部署脚本 `scripts/deploy-release.sh` 只允许目标根目录为 `/srv/bobo`，并执行：

1. 校验发布包 SHA-256 和版本清单。
2. 验证 `shared/data`、`shared/uploads` 和生产环境配置存在。
3. 将当前版本号、数据库、附件元数据和配置校验值备份到带时间戳的目录。
4. 将新版本解压到全新的 `releases/<version>`，不得覆盖已有版本目录。
5. 创建运行时数据链接并安装锁定依赖。
6. 对新版本执行语法检查和启动前检查。
7. 原子切换 `current` 链接并重启 systemd 服务。
8. 调用本机健康接口验证服务。
9. 健康检查失败时恢复旧 `current` 链接并再次重启。

部署脚本不得删除 `shared`、`backups` 或旧发布版本。旧版本清理由独立、人工确认的维护操作处理，不属于自动部署流程。

## 备份与恢复

每次部署创建：

```text
/srv/bobo/backups/<timestamp>/
├── data/
├── uploads-manifest.txt
├── environment.sha256
└── release-version.txt
```

- JSON 数据库模式复制 `shared/data` 的一致性快照。
- MySQL 模式必须使用数据库原生备份命令，禁止把 JSON 文件当作 MySQL 备份。
- 附件默认生成清单和校验值；需要完整附件备份时由显式参数启用。
- 任何备份步骤失败都会阻止部署。
- 自动回滚只回滚代码，不自动回滚数据库，以免覆盖部署后产生的新业务数据。

## 数据结构兼容

新版启动时只能执行向后兼容、可重复的结构补充，例如为旧 JSON 数据补充空的 `platformWebhookEvents` 和 `integrationNonces`。不得在普通启动流程中删除字段、重写订单号或清空业务集合。

涉及破坏性数据变更时，必须单独提供迁移脚本、迁移前备份、演练记录和回滚说明，不能夹带在普通代码发布中。

## 防误操作

脚本在以下任一条件出现时必须失败：

- 主线工作区不干净。
- 版本号已存在或与清单不一致。
- 自动化测试失败。
- 发布包包含运行时数据或敏感文件。
- 发布包或清单校验失败。
- 生产根目录不是 `/srv/bobo`。
- 正式数据目录、附件目录或环境配置缺失。
- 备份未完成。
- 服务启动或健康检查失败。

部署输出只能显示密钥是否已配置及配置文件校验值，不能显示密钥原文。

## 测试策略

新增自动化测试覆盖：

1. 干净提交可以生成发布包。
2. 工作区有修改时拒绝构建。
3. ZIP 不包含数据库、附件、配置和日志。
4. 版本清单中的提交号和文件校验正确。
5. 错误生产根目录被拒绝。
6. 备份失败时不切换版本。
7. 健康检查失败时恢复旧版本链接。
8. JSON 旧数据结构升级后原订单、工序和报工数量不变。
9. 本地平台订单、回调、历史查询和现有完整测试继续通过。

## 实施顺序

1. 冻结旧线上代码基线并生成校验快照。
2. 审核本地联调仓库所有未提交修改，按功能拆分为可追踪提交。
3. 补充版本文件和发布边界测试。
4. 实现安全构建脚本。
5. 实现服务器部署与回滚脚本。
6. 在临时目录完成一次不接触生产数据的发布演练。
7. 生成 `bobo-v0.3.0-platform-integration` 候选包。
8. 正式上线前另行执行生产备份和人工验收。

## 验收标准

- 两个目录的用途有明确文档，旧线上基线不再产生新修改。
- 本地主线所有功能修改均进入 Git，工作区干净。
- 发布包可追溯到唯一提交和版本标签。
- 发布包扫描确认不含业务数据、附件或密钥。
- 临时部署演练能够升级和回滚代码，演练数据保持不变。
- 生产部署必须经过备份、校验、健康检查和失败回滚四道门槛。
- 未经单独确认，不执行任何生产部署或生产数据库修改。
