# BOBOGD 工单业务逻辑与功能说明

更新时间：2026-08-24

本文记录当前 `bobogd` 工单系统的主要业务逻辑和功能。内容来自当前代码实现，用于后续维护、部署和需求沟通。本文不记录线上密钥、数据库密码、微信 AppSecret 等敏感信息。

## 1. 系统定位

`bobogd` 是一套轻量级钣金工单管理系统，核心目标是把订单、工单、工艺路线、派工、扫码报工、质检返工、异常闭环、图纸附件和生产看板串起来。

系统包含三类界面：

- 后台 Web：用于生产总览、订单工单、客户资料、派工路线、质检详情、客户反馈、历史查询、基础报表、操作日志和基础设置。
- 微信小程序：用于员工查看“我的任务”、扫码开始工序、报工、质检、查看生产看板和预览图纸。
- 电视看板：用于车间大屏展示生产概况、工序负荷、延期风险、近 7 日完工工单趋势和工单工序进度。

## 2. 数据源与持久化

线上运行以 MySQL 为数据源，服务端配置 `DB_DRIVER=mysql` 后，只读写 `app_state` 表中 `name=main` 的一行 JSON 状态。该 JSON 是当前业务唯一运行数据源，旁边的 `customers`、`orders`、`audit_logs` 等独立表不参与线上业务读写，不能用它们判断后台当前数据。

本地开发和自动化测试可使用 `DB_DRIVER=json`，此时读写 `data/db.json`。首次切换到 MySQL 且 `app_state.main` 不存在时，服务端可用本地 JSON 初始化该行。

业务状态顶层包含：

- `users`、`deletedUsers`
- `processes`
- `customers`
- `orders`
- `workOrders`
- `routes`
- `reports`
- `exceptions`
- `customerFeedbacks`
- `attachments`
- `drawings`
- `auditLogs`
- `settings`

图片、PDF、DWG、DXF 和生成的 CAD SVG 预览文件保存在 `public/uploads`，数据库只保存文件元数据、关联 ID 和访问路径。

## 3. 核心数据对象

当前业务围绕以下对象运转：

- 客户 `customers`：客户名称、联系人、电话、地址、备注、启停状态和停用记录。
- 订单 `orders`：订单号、客户、产品、激光编号、整数重量（KG）、数量、数量单位、交期、优先级、生产/交付状态、备注，以及发货、开票的时间和操作人。
- 工单 `workOrders`：工单号、所属订单、产品、计划数量、当前工序、状态、完成时间。
- 工艺路线 `routes`：工单内每一道工序，包含工序名、顺序、岗位、指定人员、二维码、状态、计划数量、完成数量、计划开始日、计划结束日。
- 报工记录 `reports`：每次生产报工或质检报工的数量、人员、时间、计划判定、图片和备注。
- 异常记录 `exceptions`：生产异常、质检不合格、返工关联、处理状态和处理结果。
- 客户反馈 `customerFeedbacks`：客户收货后的问题反馈，关联客户、订单、工单和具体工序，包含反馈时间、描述、照片、处理状态和处理结果。
- 图纸 `drawings` 与附件 `attachments`：工单、订单或异常相关文件，支持图片、PDF、DWG、DXF。
- 员工 `users`：账号、姓名、手机号、岗位角色、启停状态。
- 审计日志 `auditLogs`：关键管理动作记录。

## 4. 角色与权限

系统按角色和指定手机号白名单共同控制后台管理、派工、报工、客户隐私和订单交付闭环。前端是否显示入口只用于改善操作体验，最终权限由服务端再次校验。

主要角色与登录界面：

- `owner` 老板、`manager` 生产主管、`admin` 管理员：当前线上启用的完整网页后台账号所属角色。
- `office` 办公室/跟单：代码保留的受限后台角色；启用后进入网页后台，可维护客户、创建订单和查看历史，但不能编辑既有订单、查看操作日志或维护员工与标准工序。
- 车间工种角色：登录后进入手机任务/报工界面，不进入完整网页后台；包括设计、激光/切管、折弯、压铆、攻丝、焊接、机加、打磨、喷塑和装配等岗位。
- `quality` 质检：登录后进入手机任务/质检流程，同时可通过服务端读取有权限的历史工单和异常记录。

截至 2026-08-15，线上处于启用状态且可进入完整网页后台的账户角色为管理员、生产主管和老板。账户启停和角色调整以“基础设置”的当前线上数据为准，本文不固化具体账户数量。

工序和岗位有固定映射，例如设计对应设计师，激光和切管均对应激光师傅，折弯对应折弯师傅，焊接对应焊接师傅，机加对应机加师傅，质检对应质检角色。

派工逻辑：

- 若工序指定了具体员工，只有该员工或管理角色可操作。
- 若未指定具体员工，则按工序对应岗位开放给该岗位员工。
- 管理角色可操作工序，但普通员工不能跨岗位报工。
- 删除、员工角色调整、工序停用等高风险动作必须由服务端校验，不能只依赖前端隐藏按钮。

当前关键权限：

- `owner / manager / admin`：可编辑已建立订单、查看操作日志、维护员工角色和标准工序。
- `owner / manager / office / admin`：可进入后台管理框架、维护客户、创建订单并查询历史。
- `owner / manager / admin`：可维护电视看板设置；订单编辑、员工和标准工序维护均由服务端校验。

## 5. 客户、订单与工单生命周期

客户删除采用软删除：写入 `active=false`、`deletedAt` 和 `deletedBy`。停用客户不再出现在客户列表和新建订单选项中，但历史订单继续保留客户关联和显示能力。

后台新建订单时会同步生成一个工单和该工单的工艺路线。

新建订单必填：

- 订单号
- 客户
- 产品名称
- 数量
- 交期
- 至少一道生产工序

可选业务字段：

- 激光编号：原“图号”字段，保存后同步显示在工序二维码打印页。
- 重量：单位 KG，只接受大于或等于 0 的整数，不保留克级或小数精度。
- 优先级、备注和多个图纸附件。

业务规则：

- 不能只选择质检，质检前必须至少有一道生产工序。
- 质检工序会自动排在工艺路线最后。
- 已停用的工序不能被新订单选用。
- 上传的图纸会关联到订单和工单，工单中的各工序都可读取同一批图纸。

已建立订单编辑规则：

- 只有 `owner / manager / admin` 可编辑。
- 可修改订单号、客户、产品名称、数量、激光编号、重量、交期、优先级和备注。
- 可增加、移除或更换附件。
- 数量必须为大于 0 的整数；修改后同步更新订单数量、关联工单计划数量和所有非返工工序计划数量。
- 返工工序数量保持不变，数量修改不改变工序或工单状态、完成时间、已报工数量、质检数据和异常数据。
- 修改订单号和产品名称时，同步更新关联工单。
- 移除附件只写入 `removedAt` 和 `removedBy`，不立即删除磁盘原文件。

进度与状态采用两套独立计算：

- 工单进度为全部路线的 `completedQty` 合计除以全部路线的 `planQty` 合计，显示结果最高限制为 100%。
- 工单状态不根据进度百分比判断，而是根据各路线状态汇总；只有全部路线状态都是“已完成”，工单才归档为“已完成”。
- 修改订单数量时，系统按业务要求不改历史已报工数量。因此，若新计划数量小于历史完成数量，可能出现进度显示 100%，但仍有路线未完成、工单仍处于生产中的情况。
- 上述情况属于当前实现的已知数据边界。处理时应先核对各路线的计划数量、完成数量和状态，不能仅凭进度条判断工单是否完工。

工单状态由工序状态自动汇总：

- 所有工序完成后，工单状态变为已完成，并记录完成时间。
- 任一工序异常时，工单状态变为异常。
- 未全部完成且无异常时，工单处于生产中。

订单交付状态与工单生产状态分开保存：

- 工单所有工序完成后，工单始终保持“已完成”，并保存 `completedAt`。
- 订单可在生产完成后独立记录 `shippedAt/shippedBy` 和 `invoicedAt/invoicedBy`。
- 历史列表的业务状态显示优先级为“已开票 > 已发货 > 已完成”。
- 允许未发货直接标记已开票，也允许分别取消发货或开票标记。
- 发货和开票操作不重新开启工序，也不改变报工、质检、异常、返工及工单完工时间。
- 只有 5 个指定白名单账号可操作发货和开票；每次变更写入审计日志。

生产总览、订单与工单页面的活跃工单列表只展示未完成工单，并按交期从近到远排序。所有工序已完成的工单不再出现在活跃看板中，相当于进入归档/历史查询范围。

## 6. 工艺路线、派工与计划时间

每个工单包含多道路线工序。后台“派工与工艺路线”支持：

- 按工序指定具体员工，或保持按工种自动派工。
- 增加工序。
- 删除尚未开始且未报工的工序。
- 设置计划开始日和计划结束日。

标准工序顺序为：设计、激光、切管、折弯、压铆、攻丝、焊接、机加、打磨、喷塑、装配、质检。

机加规则：

- 机加使用独立的 `machining_worker` 岗位，普通员工不能跨岗位报工。
- 新建订单时机加默认不勾选；选中后按标准顺序位于焊接之后、打磨之前。
- 后续手动向工单增加机加工序时，服务端同样按标准顺序插入。
- 系统升级只补充启用的机加标准工序，不向旧订单或旧工单自动增加机加路线。

看板统计口径：

- 工单总数、正常在产、延期和今日完成均以工单为单位；正常在产、延期和今日完成互斥。
- 待加工工序和车间工序负荷以工序路线节点为单位，统计未完成工单中除“已完成”外的所有工序状态。
- 车间工序负荷包含当前在产路线实际使用的自定义或已停用工序，避免历史路线被漏统。
- 所有“今日”、近 7 日和完工日期均使用 `Asia/Shanghai` 自然日，即当日 `00:00:00` 至 `23:59:59.999`；凌晨至 08:00 的记录当然计入当天。

切管规则：

- 切管是独立生产工序，拥有独立路线、二维码、派工、排期、状态、报工、异常、返工和负荷统计。
- 切管复用 `laser_worker` 岗位，现有激光师傅可以操作激光和切管，不新增员工角色。
- 新建订单时切管默认不勾选，可以脱离激光单独选择。
- 激光和切管同时存在时，服务端固定激光在前、切管在后；派工路线后加其中一道工序时也保持该顺序。
- 系统升级只补充启用的切管标准工序，不向旧订单或旧工单自动增加切管路线。

计划时间规则：

- 计划时间精确到“日”。
- 前端展示为 `7.30-7.31` 这类格式。
- 旧数据中的 `targetFinishTime` 会兼容为计划结束日。
- 只有结束日、没有开始日的旧工序，不参与计划内外判定。
- 计划开始日不能晚于计划结束日。

## 7. 工序状态流转

普通工序状态主要包括：

- 待开始
- 进行中
- 暂停
- 已完成
- 异常

允许的状态流转：

- 待开始 -> 进行中
- 进行中 -> 暂停
- 暂停 -> 进行中
- 报工累计完成数量达到计划数量后 -> 已完成

限制：

- 待开始工序不能直接报工，必须先开始生产。
- 暂停工序不能报工，必须先继续。
- 已完成工序不能再次报工。
- 异常工序需要异常解决后恢复到进行中或已完成。

## 8. 小程序“我的任务”

小程序“我的任务”只显示当前登录用户有权限操作、且尚未完成的工序。

任务卡包含：

- 第一行单独显示“工序名 · 产品名”；产品名最多两行，超出部分省略，不能覆盖计划日期。
- 第二行采用固定栏目，依次显示工单号与剩余数量、计划日期、图纸入口和状态。
- 计划日期保持单行；无计划时显示“未排期”。
- 状态徽标固定宽度、横向显示并水平居中，不因状态字数改变位置。
- 有图纸时显示固定尺寸入口；无图纸时保留同尺寸空白占位，保证各任务卡栏目对齐。
- 完成进度。
- 开始、暂停、继续、去报工等按钮。
- 质检工序额外显示当前可送检数量。

图纸预览逻辑：

- 同一工单上传的图纸同步给该工单下的所有工序任务。
- 小程序任务卡只显示预览入口，不在生产看板卡片中显示预览/下载按钮。
- 点击后进入附件清单，必须展示该订单全部有效附件；图片预览支持在全部图片之间左右滑动。
- 预览页提供下载按钮，下载前有二次确认，防止误触。

## 9. 扫码开始与扫码报工

工序二维码包含工序 token。扫码入口支持从二维码链接或 token 中解析出工序。

扫码逻辑：

- 如果工序尚未开始，会弹窗提示是否立即开始生产。
- 确认后将工序状态改为进行中，并进入与小程序内部扫码一致的任务/报工流程。
- 如果工序已进行中，则进入报工。
- 如果工序暂停或已完成，会按状态提示，避免重复或错误报工。

微信直接扫码和小程序内扫码的显示与跳转逻辑需要保持一致。

## 10. 生产报工逻辑

普通生产工序报工字段包括：

- 本次完成数量
- 返工数量
- 备注
- 异常类型
- 异常描述
- 现场图片

校验规则：

- 本次完成数量必须大于 0。
- 返工数量不能小于 0，且不能超过本次完成数量。
- 累计完成数量不能超过工序计划数量。
- 报工人由当前登录用户确定。

报工后：

- 系统增加一条报工记录。
- 工序累计完成数量增加。
- 记录最后报工时间和最后报工人。
- 累计完成达到计划数量时，工序变为已完成。
- 若填写异常类型或异常描述，创建异常记录，并将工序置为异常。

## 11. 报工计划判定

每次报工都会保存当次计划时间快照和实际报工日。

保存字段包括：

- 计划开始日
- 计划结束日
- 实际报工日
- 报工人
- 计划判定
- 超计划原因

判定规则：

- 无完整计划起止日：记为未排期，不参与超计划统计。
- 实际报工日早于计划开始日：视为正常，前端显示绿色。
- 实际报工日在计划开始日和计划结束日之间：视为计划内，前端显示绿色。
- 实际报工日晚于计划结束日：视为计划外，报工日期显示红色。
- 计划区间包含起止当天。

基础报表页面的时间显示保持原有格式不变。CSV 导出会增加计划开始日、计划结束日、实际报工日、计划判定、超计划原因等统计字段。

## 12. 质检报工、返工与异常闭环

质检工序是正式工序，不只是手工登记异常。后台质检和小程序质检最终都通过正式报工接口提交。

质检开放条件：

- 工单必须有质检工序。
- 质检前一道生产工序必须已完成。
- 质检可送检数量大于 0。
- 问题工序和返工工序只能从该工单内已完成的生产工序中选择，不使用全局工序库。

质检报工字段包括：

- 本次送检数量
- 本次检验数量
- 合格数量
- 不合格数量
- 处置方式
- 问题工序
- 返工工序
- 问题说明
- 问题图片

质检校验规则：

- 送检数量和检验数量必须大于 0。
- 检验数量必须等于送检数量。
- 合格数量 + 不合格数量必须等于检验数量。
- 不合格数量大于 0 时，必须选择处置方式、问题工序并填写问题说明。
- 处置方式为返工时，必须选择返工工序。
- 可送检数量受前一道生产工序完成数量、已送检数量和已完成返工数量共同限制。

后台质检特殊逻辑：

- 后台提交质检时，如果质检节点仍为待开始，管理端可自动开启质检节点后提交报工。
- 手机端不自动开启，仍要求按现有流程先开始生产。

质检结果处理：

- 全部合格：质检报工计入完成数量，达到计划数量后质检工序变为已完成。
- 让步接收：不合格数量也计入质检完成。
- 报废：不合格数量不计入完成，生成异常记录。
- 返工：系统在质检前插入返工工序，返工完成后相关异常进入已解决/等待复检闭环。

异常联动：

- 质检不合格会创建异常记录，保存 `qualityRouteId` 和 `issueRouteId`。
- 未解决的质检异常会让质检工序椭圆显示紫色泛光。
- 被选为问题工序的工序文字显示紫色泛光。
- 异常解决后，紫色高亮自动消失。

## 13. 质检详情、异常返工与客户反馈

后台“质检详情”保留原异常返工业务，包含两部分：

- 后台质检报工表单。
- 异常列表和处理入口。

异常来源：

- 生产报工时填写异常信息。
- 后台或小程序质检发现不合格。
- 管理/质检角色手工登记异常。

异常处理：

- 管理、质检、老板、管理员可处理异常。
- 异常解决后记录处理说明、处理人和处理时间。
- 如果异常对应的工序处于异常状态，解决后根据完成数量恢复为进行中或已完成。

客户反馈是生产质检之外的独立售后记录：

- 菜单仅对 5 个指定白名单账号显示，查询、创建和处理接口也执行同一白名单校验。
- 录入时先选择客户，再选择该客户已经完成生产的订单工单，最后选择该工单中的真实问题工序。
- 反馈时间和问题描述必填，可上传多张问题照片；创建后默认状态为“待处理”。
- 填写处理结果后可标记为“已处理”，系统保存处理人和处理时间。
- 创建和处理动作均写入审计日志。
- 历史工单的“异常记录”同时聚合质检异常与客户反馈；非白名单账号只能读取质检异常，不能读取客户反馈数据。

## 14. 图纸与附件

图纸上传入口主要在后台新建订单/工单流程中。

支持格式：

- 图片：png、jpg、jpeg、gif 等。
- PDF。
- CAD：DWG、DXF。

后台附件入口：

- 生产总览、订单工单、历史查询统一使用一个固定尺寸的“图 + 附件数量”入口，不再为每个附件重复排列“预览 / 下载”按钮。
- 质检异常、异常详情和客户反馈的问题照片使用同一附件组入口；无附件显示“无”。
- 附件数量以角标显示，超过 99 个显示 `99+`；附件数量不同不会增加表格行高。
- 编辑订单显示附件组预览入口，同时保留逐文件移除勾选；移除仍采用软删除。
- 下载操作集中在预览窗口内，下载文件名保持原文件名。

统一预览窗口：

- 后台和交互式横屏看板使用深黑蓝背景、青色边框的统一预览窗口，顶部显示工单号、产品名称、当前文件名、下载和关闭按钮。
- 多附件时显示系统左侧文件列表并支持切换；只有一个附件时隐藏文件列表，让预览区域占满可用宽度。
- 图片等比例展示；DWG、DXF 继续使用生成的 CAD SVG 预览。
- 桌面后台、普通浏览器后台手机横屏和派工看板中的 PDF 使用浏览器原生 `iframe`，默认追加适应页面、第一页和尽量隐藏侧栏的参数。
- Android 平板专用 APP 使用 GeckoView 打开后台；看板 PDF 优先使用 `iframe`，加载异常或超时后切换 PDF.js `canvas`，并提供“兼容预览”手动切换入口。
- 浏览器原生 PDF 工具栏和缩略图栏由浏览器控制，URL 参数只能尽量设置默认状态，少数浏览器可能忽略或恢复用户上次设置。
- 小程序紧凑横屏不使用原生 PDF `iframe`，而使用项目内置 PDF.js 将单页绘制到 `canvas`，支持上一页、下一页、页码和缩放；失败时显示明确错误。

CAD 预览逻辑：

- 上传 DWG/DXF 后，服务端尝试使用本地 `dwg2SVG` 生成 SVG 预览文件。
- 原始 CAD 文件继续保留，用于下载。
- 预览按钮优先打开生成的 SVG。
- 如果 SVG 不存在，小程序或后台可调用 CAD 预览生成接口尝试重新生成。
- 转换失败时提示 CAD 预览生成失败，不把下载伪装成预览。
- 线上服务器需要安装 `libredwg-tools` 并提供 `dwg2SVG` 命令，否则 CAD 原文件下载可用，但预览不可用。

小程序普通页面预览逻辑：

- 普通图片直接调用 `wx.previewImage`，传入该订单全部图片 URL。
- PDF 下载临时文件后调用 `wx.openDocument`。
- DWG/DXF 优先打开 SVG 预览页。
- CAD 原文件下载完成页提供“本地打开”和“转发文件”。DWG/DXF 不属于微信稳定支持的文档格式，本地打开失败时明确提示使用转发文件，不把兼容失败误报为下载失败。
- 下载前统一弹窗确认。
- 真机预览需要确保文件域名、downloadFile 合法域名、web-view 合法域名配置正确。

## 15. 看板逻辑与隐私

看板客户隐私规则：

- 小程序竖屏看板：只有上述 5 个指定账号显示客户名称。
- 手机横屏看板：登录后先向 `/api/tv-viewer-token` 获取 12 小时签名令牌；只有上述 5 个指定账号的有效令牌可获得客户名称。
- 电视看板、无令牌访问、无效令牌和过期令牌：服务端移除客户名称及其他客户资料。
- 客户脱敏在 `/api/tv-dashboard` 服务端完成，不能通过修改前端查询参数绕过。

### 派工看板

- 生产总览中的“派工看板”仅对上述 5 个指定账号显示和开放。
- 派工看板复用手机横屏看板布局，但使用独立的 12 小时签名令牌和操作接口；普通手机横屏看板、电视看板保持只读。
- 灰色且状态为“待开始”或“暂停”的工序可单击切换为“进行中”；黄色且状态为“进行中”的工序可单击切换为“暂停”。
- 红色延期、绿色完成、浅蓝部分报工、紫色质检异常以及异常、返工节点不可点击。
- 切换的是实际生产状态，会同步影响报工权限、工单状态及所有看板；当前派工看板立即刷新，其他看板按各自刷新周期同步。
- 后端校验账号白名单、令牌用途、工序旧状态和允许的状态转换；并发状态冲突时拒绝操作并要求刷新。
- 每次派工看板状态切换写入审计日志，记录操作人、工序及切换前后状态。

### 电视看板

电视看板数据来自 `/api/tv-dashboard`。

显示内容：

- 生产概况统计。
- 准时率仪表。
- 工单状态分布。
- 车间工序负荷。
- 近 7 日完工工单趋势。
- 活跃加工工单列表。

排序与归档：

- 只展示未完成工单。
- 按交期从近到远排序。
- 延期、48 小时内加急、急单会有不同提示。
- 已完成工单不再进入活跃列表。

工序节点显示：

- 节点为横向椭圆。
- 椭圆内显示计划时间区间。
- 不显示原来的 100% 文案。
- 节点下方显示工序名。
- 最近一次报工显示为“报工日 + 报工人”，同一行显示。

颜色规则：

- 已完成或计划内/提前报工：绿色。
- 未完成且计划结束日早于服务器当前自然日：红色；部分报工仍为红色，全部完成后恢复绿色。
- 进行中扫码开始：黄色椭圆和黄色泛光。
- 待开始：保留待开始样式。
- 晚于计划结束日报工：报工日期红色，外框仍按完成态显示绿色。
- 未解决质检异常：质检节点紫色泛光，问题工序文字紫色泛光。

图纸入口规则：

- 后台手机横屏、派工看板和小程序紧凑横屏在产品信息第三行右侧显示“图 + 附件数量”，与左侧数量和单位水平对齐。
- 无附件时保留同尺寸空白位置，避免产品、客户和数量发生位移。
- 图纸入口不增加工单行高，不改变产品列、进度列、工序列或交期列宽。
- 普通电视大屏保持纯展示，不返回图纸元数据，也不显示图纸入口。
- 看板图纸、原文件下载和 CAD 预览继续校验有效看板令牌；伪造、缺失或过期令牌不能读取附件。

### 小程序横屏看板

小程序横屏看板与电视看板保持同一套业务语义：

- 工序椭圆显示计划区间。
- 不显示完成百分比。
- 报工日精确到日。
- 报工人显示在报工日旁边。
- 质检异常联动紫色高亮。
- 每次约 15 秒自动刷新前，页面按工单保存工序栏的横向滚动位置；重绘后分别恢复并限制在有效滚动范围内。
- 普通手机横屏看板和派工看板共用位置保持逻辑；刷新数据不会把当前查看的工序重置到最左侧，关闭页面后不保留位置。
- 小程序紧凑横屏使用独立 `compact=1` 模式，只缩小小程序看板，不改变后台手机横屏、派工看板和普通电视大屏。
- 紧凑模式以一屏约 7 道工序为目标：工序节点宽 60px、椭圆宽 58px、工序间距 3px，超出部分继续左右滑动。
- 紧凑模式的“图”按钮和数量角标单独缩小并固定在第三行，不能遮挡第二行客户名称。

### 完工时间与近 7 日统计

- 工单完工时间取工单 `completedAt`；当全部路线完成时写入。旧数据缺少该字段时，兼容取各路线最后完成/报工时间中的最晚时间。
- 顶部“今日完成工单”、近 7 日折线图和后台已完成统计均按工单完工时间统计工单数量，不按报工记录条数或报工数量统计。
- 近 7 日趋势为包含今天在内连续 7 个自然日，每个工单只计入其完工日期对应的一天。
- 工单后续标记为已发货或已开票不会改变 `completedAt`，仍归入原完工日期。

### 小程序生产看板

手机竖屏“生产看板”用于快速查看工单状态和工序进度。

当前保留原有看板卡片结构：

- 产品/工单/客户/交期。
- 状态标签。
- 工序进度条。
- 当前工序与进度。

看板只显示未完成工单，已完成工单进入历史归档。生产看板不显示图纸预览或下载操作区。

所有打印的工序二维码页面不显示客户名称，只显示工单号、产品、交期、数量、激光编号、订单备注、工序及完成状态。右上角原静态打印说明已替换为“订单备注”：内容读取订单唯一字段 `order.note`，空值显示“无备注”，文本经过转义并保留人工换行，长内容自动换行并分档缩小字号。订单编辑保存备注后，刷新或重新打开二维码打印页即可读取最新内容，不向工单或工序复制备注。

## 16. 后台功能模块

后台主要页面：

- 生产总览：统计当前生产、延期、异常、工序负荷，并展示未完成工单进度。
- 客户资料：维护客户基础信息。
- 订单工单：新建订单、上传图纸、选择工艺路线、查看未完成工单。
- 派工路线：给每道工序派人、调整计划起止日、新增/删除工序、打印工序二维码。
- 质检详情：后台质检报工、质检异常列表、返工和异常处理。
- 历史查询：查询历史工单、报工、异常等记录。
- 历史查询支持按创建时间、交期时间或完工时间及起止日期筛选，并可按生产中、已完成、已发货、已开票筛选。
- 历史工单显示重量、完工时间和异常记录；质检异常与客户反馈通过“详情”弹窗集中追溯。
- “异常返工”菜单更名为“质检详情”，原质检报工、异常和返工逻辑保持不变。
- 现有 5 个高权限白名单账号可使用“客户反馈”，按客户、已完成订单工单和问题工序登记反馈，并完成待处理到已处理的闭环。
- 已完成订单可独立标记已发货和已开票，显示优先级为已开票、已发货、已完成；交付标记不改变工单及工序的生产完成状态。
- 生产总览的已完成工单默认统计包含今天在内的最近 7 个自然日，并可按完工起止日期调整后跳转历史列表。
- 基础报表：查看报工记录，导出 CSV。
- 操作日志：仅 `owner / manager / admin` 可见，可按日期、操作者、动作和关键词筛选并分页查看。
- 基础设置：维护员工账号和多岗位角色、标准工序启停、电视看板轮播参数等；员工停用或角色不再匹配时，会清除其尚未完成工序上的无效指派。

## 17. 操作日志

关键业务变更通过 `auditLogs` 记录：

- 登录、退出。
- 客户、订单、附件、员工、角色和工序维护。
- 派工、排期、状态流转、报工、质检、异常和设置变更。
- 强制删除和其他高风险操作。

日志保存操作者、动作、对象、时间及修改前后摘要，不保存密码、Base64 文件内容和其他大字段。日志保留两年，每次写入时清理超过保留期的数据。普通 `/api/bootstrap` 不返回 `auditLogs`，无权用户访问 `/api/audit-logs` 返回 403。

## 19. 部署与运行注意事项

后端：

- 主入口是 `server.js`。
- Web 静态文件在 `public`。
- 小程序代码在 `miniprogram`。
- 线上使用 MySQL `app_state.main`；本地开发和测试可使用 JSON。
- PM2 进程名线上通常为 `bobogd`，但实际查询时应以 `pm2 list` 的 id/name 为准。

微信小程序：

- 小程序端代码修改后，需要在微信开发者工具重新上传并发布。
- 图片、PDF、CAD 预览涉及合法域名配置。
- `web-view` 预览 SVG 时，需要把业务域名配置到小程序 web-view 合法域名。
- 真机上图片空白时，优先检查图片 URL 是否 HTTPS、是否在合法域名内、服务器是否返回正确的图片 `Content-Type`、是否允许小程序访问。

CAD：

- DWG/DXF 预览依赖服务器本地 `dwg2SVG`。
- 转换结果可能受 CAD 文件复杂度影响。
- 即使 CAD 预览失败，原文件下载仍应可用。

安全：

- 文档和代码提交时不要写入 AppSecret、数据库密码、微信密钥等敏感信息。
- 线上环境变量和 PM2 ecosystem 配置应在服务器上单独维护。
- `TV_VIEW_TOKEN_SECRET` 用于签发看板身份令牌；应在服务器独立配置并定期更换。

## 20. 数据维护边界

- 线上业务数据以 `app_state.main` 为准，修改独立业务表不会同步到后台。
- 删除生产数据前必须先备份 MySQL `app_state` 的 `main` 行和 `public/uploads`。
- 客户和附件采用软删除，历史工单、审计记录和磁盘原文件默认保留。
- 已完成工单正常归档，不应为了让它从看板消失而直接删除数据。
- 文档只记录结构和规则，不固化会变化的客户数、订单数、工单数和生产统计；实时数量以后台和 `/api/tv-dashboard` 为准。
